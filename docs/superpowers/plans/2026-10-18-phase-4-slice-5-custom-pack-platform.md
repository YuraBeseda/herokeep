# Phase 4 Slice 5 — Custom Pack Platform Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**STATUS: WRITTEN 2026-10-18 — executing per the standing autonomous loop (plan 14 merged @ 7a07ee1).**

**Goal:** Ship the remaining Phase 4 roadmap deliverable — custom content packs end to end: import a `.hkpack` or `pack.json` with full validation and a trust screen, pin packs per character (the content index becomes per-character), update a pinned pack through the documented rebase flow with a report, carry non-core packs inside `.hero` bundles, author quick homebrew (item, spell, feat, species) as a local content pack, and build `.hkpack` files with pack-tools.

**Architecture:** Everything the platform needs already exists in the engine as mechanism (`createContentIndex(packs, {pins, roots})`, `selectPackVersions`, `validatePack`, `Facts.pins` from `pack.pinned@1`); the web app simply never used it (one global index, no import path, no pin events). This plan wires the data flow: a browser-side reader (fflate, mirroring the `.hero` reader) validates everything before storage; `PackStore` keeps content packs and their assets (`BlobRow.origin: 'pack'`); `EngineFacade.indexFor(pins)` memoizes a per-character index and `derive` runs against it; a new pure `planRebase` in the engine computes the sheet diff, invalid decisions and `deprecated.replacedBy` migrations and emits the single rebase transaction the architecture doc specifies; homebrew is just a locally authored content pack (`homebrew`) whose saves bump the patch version and fast-forward pinned characters through the same rebase planner. Campaign relay of packs (server storage) is explicitly out of scope and owner-flagged.

**Tech Stack:** Existing monorepo (TS 6, Vitest 4, Zod, Angular 22 zoneless, Playwright, Dexie, fflate 0.8.3 already in `apps/web`). ONE new dependency allowed: `fflate` added to `@hk/pack-tools` (same version) for the zip build.

**Spec:** `docs/02-architecture/04-content-packs.md` (§Distribution :29-30, §Overrides :534-540, §Versioning and rebase :554-562, §Validation levels :564-570, §Authoring :572-577), `docs/01-decisions/ADR-008-extension-format-and-safety.md` (:81-111 — report shape, cancel keeps pin, unresolved-reference chip, validate before store, size caps, enable screen contents), `docs/02-architecture/09-frontend-architecture.md` (:31-49 — `packs/ installed, import, quick-homebrew`, `PackStore … enabled sets`), `docs/02-architecture/07-images-and-blobs.md:77-80`, `docs/03-roadmap/phases.md:14`. ## Design rulings (baked in — verify cited data, do not re-litigate)

1. **`.hkpack` = ZIP with `pack.json` at the root + `assets/<hash-hex>` entries** (doc-04 :29-30; `<hash-hex>` is the 64-hex part of `sha256:<hex>`). A bare `pack.json` file is also importable (same pipeline minus the zip step). No separate manifest file: `pack.json` IS the manifest. Constants live in `packages/protocol/src/bundle/hkpack.ts`: `HKPACK_PACK_ENTRY = 'pack.json'`, `HKPACK_ASSET_DIR = 'assets/'`, `HKPACK_LIMITS = { maxEntries: 2001, maxAssetBytesTotal: 64 * 1024 * 1024, maxZipBytes: 72 * 1024 * 1024 }` (ruling 2 caps — OWNER-FLAG: ADR-008 caps per asset only; the container totals are this plan's choice).
2. **Import pipeline order (fail fast, store nothing until the end):** size caps → unzip → required entry → `parsePack` (schema) → `validatePack(pack, [core, ...installed content packs])` (semantic; errors block, warnings are shown on the trust screen) → every `assets[]` entry has a zip entry, its bytes ≤ `size`, mime check, sha256 matches → id@version conflict check (same `id@version` already installed with a different canonical JSON → refuse; identical → no-op "already installed") → ONLY THEN `PacksRepository.putPack` + `BlobsRepository.put` (origin `'pack'`, kind from the asset, `pinned: false`). Error classes carry i18n codes `packs.import-failed-{too-large,bad-zip,missing-pack-json,bad-schema,invalid,asset-missing,asset-too-large,asset-hash-mismatch,conflict}` exactly like `HeroImport*Error` carries `characters.list.toast.import-failed-*`.
3. **Installed ≠ enabled.** Installing a pack makes it available on the device; a CHARACTER opts in by pinning it (`pack.pinned@1 {packId, version}`) and opts out with the new additive `pack.unpinned@1 {packId}` (reducer deletes `pins[packId]`; core cannot be unpinned — `propose.unpinPack` refuses the core pack id). The per-character content index = `createContentIndex(allInstalledPacks, { pins: facts.pins, roots: Object.keys(facts.pins) })` plus the translation packs that translate any selected pack (verify `resolveDependencyOrder` already follows `translates`; if roots exclude translations, add them to roots in `EngineFacade.indexFor`). Legacy characters have only the core pin → the same set as today → byte-identical sheets (72 goldens + a replay test).
4. **Pins are the truth, the pack set is derived from them.** `EngineFacade.indexFor(pins: Pins): ContentIndex` memoizes by the canonical pins key; `CharacterStore` derives with `indexFor(facts.pins)`; the create wizard derives drafts with `indexFor({ [core]: version, ...selectedContentPacks })` and emits `character.created` followed by one `pack.pinned` per selected content pack in the SAME creation transaction. `foreign-character-session.ts:345` (exact core version mismatch → error) stays as is.
5. **Rebase is an engine-pure plan, the web only renders and commits it.** `planRebase(facts: Facts, current: ContentIndex, next: ContentIndex, nextPins: Pins, rules?: Rules): RebasePlan` where `RebasePlan = { changes: SheetChange[]; invalid: InvalidDecision[]; migrations: Migration[]; events: EventInput[] }`, `SheetChange = { path: string; before: unknown; after: unknown }` (leaf dot-paths over the derived Sheet, sorted, provenance/`sources` subtrees excluded so the report lists VALUES), `InvalidDecision = { choiceId: string; selection: string[]; reason: 'choice-missing' | 'selection-missing' | 'selection-deprecated' | 'prerequisite-failed' }`, `Migration = { choiceId: string; from: string; to: string }` (via `deprecated.replacedBy` on the selected entity in `next`), `events` = one `pack.pinned@1 {packId, version, previous}` per changed pin + one `pack.unpinned@1` per removed pin + `decision.made@1` with the migrated selection per Migration + `decision.cleared@1` per InvalidDecision that has no migration (doc-04 :554-562, ADR-008 :85-92). Deterministic; no I/O.
6. **Core pack versions:** the app serves only the shipped core version (`PACK_VERSION`). A character pinned to an older core (after an app update) derives against the shipped core (`selectPackVersions`: exact pin missing → `deps.pinMissing` diagnostic + highest available — verify) and the Build tab shows "Update available" for the core with a VALIDATION-ONLY report (old core not retained on device → no sheet diff; the report says so). OWNER-FLAG: ADR-008 :81 says devices keep every pinned version; retaining old core versions is a later slice. Core version is still 0.1.0, so this path is tested with fixtures, not real data.
7. **Removing an installed pack** that characters still pin is allowed (ADR-008 :93: a missing entity renders an "unresolved reference" chip): the detail screen shows the count of pinning characters and a warning; after removal those characters show the missing-pack banner (ruling 8) and unresolved chips; sheets never crash (derive already emits `derive.unresolvedEntity` / `selection.unresolved` warnings).
8. **Missing-pack banner:** when `facts.pins` names an `id@version` not installed (sync restore on a new device, `.hero` import without the pack, removal), the sheet shows a banner naming the pack and version with a link to `/packs`; the banner is data-driven from `pins` vs `PackStore.installed()`.
9. **`.hero` bundles carry every non-core pinned pack:** writer adds `packs/<id>@<version>.json` (canonical JSON) + the pack's assets under the existing `assets/` convention + manifest additive `packs?: Array<{ id, version, path, sha256 }>`; reader validates each (schema + `validatePack` against core + bundle packs + sha256) and installs the ones not present, refuses on `id@version` conflict (`import-failed-pack-conflict`). Old bundles without `packs` import exactly as before.
10. **Homebrew = one local content pack `homebrew`** (`PACK_ID_RE` ok; `kind: 'content'`; `system` = the core pack's system entity slug — read it from the loaded core, never hard-code; `dependencies: [{ id: core id, range: '^<core version>' }]`; `version` starts `0.1.0` and every save bumps PATCH). Entity ids `homebrew:<type>/<slug>`; slug = ASCII slug of the name (lowercase, `[a-z0-9-]`), Cyrillic transliterated with a small ru/uk table, collision → `-2`, `-3`; empty result → `<type>-<n>` (OWNER-FLAG: transliteration table is a convenience, not a standard). Four forms (item, spell, feat, species) produce entities valid under `ItemEntitySchema`/`SpellEntitySchema`/`FeatEntitySchema`/`SpeciesEntitySchema` with text-only mechanics (`feature.text` for traits/feat text) EXCEPT the structural fields those schemas require (item category + weapon/armor subfields, spell level/school/components, species size/walk speed). Save = replace-or-add the entity → `parsePack` the whole pack → `validatePack` → store → for each character pinning `homebrew`: `planRebase(...)`; if `invalid.length === 0` commit the plan's events silently (visible in the timeline as `pack.pinned`), else leave the update badge for the player. Delete asks confirmation and goes through the same path (invalid decisions then surface in the report).
11. **pack-tools zip build:** `runBuild({ dir, out?, packsDir?, zip?: boolean })` writes `dist/<id>-<version>.hkpack` when `zip` is set (deterministic: entries sorted, fixed mtime, `pack.json` canonical) and `runValidate` accepts a `.hkpack` path (unzips `pack.json`, verifies asset hashes). The e2e/web fixture `.hkpack` files are produced by this command from checked-in source folders, so the two zip writers (node + nothing else — the web never writes `.hkpack`) stay one.
12. **Out of scope, owner-flagged:** campaign pack relay/server storage of pack JSON (`pack.enabled@1` exists; the DO stores nothing — ADR-008 :81-84 and doc-07 :77-80 describe an unbuilt design; Task 9 corrects doc-07's claim that `pack.enabled` carries a manifest); community registry (Phase 7); retaining old core versions (ruling 6); Web Worker derive (perf 0.471 ms).
13. **No speculative vocabulary.** Every mechanism ships with a real consumer in the same task (the sample content pack, the homebrew pack, the rebase fixtures) and a test pins it.

## Review Focus

1. A legacy character (core pin only) derives byte-identically against the per-character index — 72 goldens + an explicit replay test comparing `derive(facts, globalIndex)` vs `derive(facts, indexFor(facts.pins))` over every golden fixture (Task 4).
2. A malformed import stores NOTHING: oversize zip, missing `pack.json`, schema failure, dangling reference, asset hash mismatch, `id@version` conflict — after each refusal `PacksRepository.getAll()` and the blobs table are unchanged (Task 2).
3. Rebase v1→v2 with a renamed entity (`deprecated.replacedBy`) migrates the decision, and the resulting log replays to the same sheet as a fresh pick of the new entity; Cancel leaves `pins` unchanged (Tasks 1, 5).
4. Removing a pinned pack (or restoring a character whose pack is absent) leaves the sheet renderable: banner + unresolved chips, no exception, derive warnings only (Tasks 3, 4).
5. A homebrew save with three characters pinning `homebrew` fast-forwards all three with exactly one `pack.pinned` each and zero invalid decisions; a save that DELETES an entity one of them uses does NOT auto-commit for that character and shows the badge (Task 7).
