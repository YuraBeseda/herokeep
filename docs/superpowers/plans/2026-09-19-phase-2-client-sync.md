**Architecture:** Auth is cookie-based same-origin (ADR-012; PBKDF2 verifier derived in the browser). Sync integrates at CharacterStore's serialized queue: when authed, local appends become PENDING rows (the seq-less `pendingOrder` machinery EventsRepository has carried since plan 4), the SyncService's socket flushes them (`hello.pending`/`append`), acks call `assignSeqs`, rejects drop+rederive+toast; server `events` frames apply through `runExclusive`. Logged-out = today's committed-local mode; login transitions each stream once (upload). One socket per device per stream via Web Locks; follower tabs get events via BroadcastChannel.

**Tech Stack:** Existing (Angular 22 zoneless/signals, Transloco, Dexie). Native WebSocket + WebCrypto (no new runtime deps). Top-10k password list as a bundled asset (source verified at execution). e2e gains a real-API project (Node adapter + a small static+proxy server).

### Design rulings baked into this plan

1. **Sync state lives in a dedicated `SyncService` + per-stream `StreamSyncSession`**, NOT inside CharacterStore. CharacterStore gains a minimal seam: (a) `appendTx` writes PENDING rows (no local seq) when `SyncService.isSyncing(streamId)`, else local-committed exactly as today; (b) a store-exposed hook to apply server-committed events + acks under `runExclusive`. Revert/undo flows produce events like any append — no special-casing (`event.reverted` is just an event on the wire).
2. **Snapshots and sync**: on any server-driven history change (restore, seq rewrite, reject-drop), drop the snapshot and full-replay (plan-4 revert contract, reused). Steady-state ack-at-expected-seq keeps the snapshot.
3. **AuthService boot**: `GET /api/me` ONCE at app init, non-blocking, network-failure-tolerant (offline → logged-out UI state with a "last known" hint; NEVER a spinner wall). Signals: `user: Signal<{userId, username}|null>`, `status: 'unknown'|'authed'|'anon'`.
4. **The leader/writer relationship**: only the WRITER-lock-holding tab (existing `hk-writer` LeaderService) runs sync sessions; the per-stream `hk:sync:<id>` lock guards against multi-DEVICE… no — it's per doc-03 the per-tab socket guard. Ruling: sync sessions run only in the leader tab (one lock acquisition path, reuses LeaderService), and `hk:sync:<streamId>` is still acquired per stream as doc-03 specifies (cheap, future-proof for non-leader scenarios); follower tabs mirror via BroadcastChannel channel `hk:events:<streamId>` carrying applied committed events (payload: the events — followers apply to their in-memory signals only; Dexie is shared).
5. **Password list asset**: `assets/auth/top-10k-passwords.txt` (newline-separated, lowercase), fetched lazily on the register screen, checked case-folded. Source: a canonical public top-10k list — executor verifies the exact source/license at execution and records it (SecLists' 10k most common is the default candidate).
6. **Device label** at login/register: navigator hints (`platform`/UA brand) + user-editable text input, default like "Chrome on Windows"; sent as `deviceLabel`.
7. **e2e strategy**: a SECOND Playwright project `sync` with its own config: webServer[0] = the Node API adapter (seeded temp data dir, ephemeral fixed port), webServer[1] = a tiny static+proxy server (`apps/web/tools/serve-with-proxy.mjs`: serves dist, proxies `/api` HTTP+WS to the adapter — ~60 lines, no new deps beyond what exists; http-proxy NOT added unless truly needed — node http + ws piping; executor may use the `serve` package for static + manual proxy routes). The default e2e project stays untouched and offline-pure.
