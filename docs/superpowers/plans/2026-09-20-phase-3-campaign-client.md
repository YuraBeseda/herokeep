- Campaign socket protocol (doc-03 verbatim, all shapes already in `@hk/protocol` sync/messages.ts): client sends `hello {streams, have, pending}`, `append`, `subscribe/unsubscribe {stream, lastSeq?}`, `blob.have/request/cancel`, `presence {state}` (throttle ≥60 s), binary `blob.chunk`; receives `welcome`, `events`, `ack/reject`, `members`, `blob.pull/chunk/unavailable`, `notice`, `bye {reason}`. Gap rule: `seq != lastSeq+1` → re-send `hello` for that stream, never guess. Reconnect triggers + backoff (0.5 s × 2ⁿ ±20 %, cap 30 s) exactly as plan 8 shipped. `bye` with reason `campaign.member_removed` (exported `BYE_REASON_MEMBER_REMOVED`) → leave the campaign UI + toast; server closes with WS code 4000.
- Visibility is SERVER-enforced; the client (a) sets `visibility` on `roll.logged`/`chat.message` it authors (default from `settings.visibility.rolls`; `private` offered only when `allowPrivateRolls`), (b) renders whatever arrives, (c) never assumes it has the full log (filtered catch-up is normal).
- Blob transfer client (doc-07 verbatim): announce `blob.have` on connect and after each completed download (own character's blobs + campaign-announced hashes the device holds); serve `blob.pull` one-at-a-time per holder queue by streaming binary chunks with the EXACT server codec — reuse `BLOB_CHUNK_MAGIC` (`"HKBC"`), 16-byte big-endian header `[magic 4B][index u16][total u16][to u32][hashPrefix 4B]`, ≤64 KB payloads, 0-based index, completion = `index === total-1` (import these constants from `apps/api`?? NO — core boundary: copy the canonical values into a client module with a cross-referencing comment AND a test pinning byte-for-byte equality against a fixture frame, since `apps/web` cannot import `apps/api`); requester assembles, verifies SHA-256 of the whole payload BEFORE storing, discards+retries on mismatch; one blob in flight per requester; request timeout → `blob.cancel` → re-request with backoff and on `members` updates (server may re-pick the same holder — `selectHolder` has no exclusion list; the client's only lever is cancel+retry timing, document honestly). Prefetch tiers P1→P4 per doc-07's table; P4 (every announced blob, idle, continuous) is DM-only super-peer. Cache: Dexie `blobs` gains `addedAt/lastUsedAt/pinned/origin` + kinds `icon|banner`; pinned = own + current campaign; LRU cap default 500 MB with a Settings slider 100 MB–2 GB showing `navigator.storage.estimate()`; weekly orphan sweep.
- Campaign quotas surface in UI: welcome's `quota {bytesUsed,bytesMax,eventCount}` per stream (SyncService already exposes `quotaFor`); 12-member cap and join-closed produce server errors the join screen must render distinctly.
- e2e: extend the REAL-API sync project (`playwright.sync.config.ts`, workers 1) with two-browser-context campaign scenarios (DM + member). The offline default project gets no campaign specs (campaigns are online-only).

### Design rulings baked into this plan

1. **Projection, not reduction**: new pure module `apps/web/src/app/shared/services/campaigns/campaign-projection.ts` — `projectCampaign(events: EventEnvelope[]): CampaignState` where `CampaignState = {name, system, settings: CampaignSettings|null, joinCode?: string, members: Map<userId,{displayName, role, removed: boolean}>, roster: Map<characterId,{ownerId, name, left: boolean}>, packs, overviews: Map<characterId, PartyOverview>, session: {active: boolean, startedAt?: eventId, title?: string}, log: LogEntry[] (rolls+chat+session markers in seq order), dmNotes: Map<id,{title?,body?}>, archived: boolean}`. Deterministic, tolerant of unknown types (skip), tested standalone. `@hk/engine` untouched.
2. **Stream-kind widening**: `SYNC_WS_URL_FN` becomes `(streamId: string) => string`; new `wsUrlForStream(streamId)` maps `char:<id>` → `/api/characters/<id>/ws`, `camp:<id>` → `/api/campaigns/<id>/ws` (existing `wsUrl(characterId)` delegates, callers migrated). `StreamSyncSession` gains optional hooks `{onMembers?(members), onForeignEvents?(stream, events), onBinaryFrame?(bytes), onNotice?(notice)}` and a `sendRaw(msg: ClientMessage)`/`sendBinary(bytes)` surface for subscribe/blob traffic; `WS_MESSAGE_BYTES_MAX` is hoisted to `@hk/protocol` (closes the plan-8 duplication flag) with api+web importing it.
3. **CampaignStore** (`shared/stores/campaign.store.ts`) implements the SAME `StreamSyncSessionStorePort` shape CharacterStore does (`applyServerCommit/commitPending/dropPending/onLocalAppend`), persists campaign events in the existing Dexie `events` table under `camp:<id>`, exposes `state: Signal<CampaignState|null>` via the projector, `appendTx(drafts)` for campaign events, and `gatewayAppend(characterId, drafts): Promise<AckOrReject>` which routes char-targeted events through the campaign socket (rid-scoped ack routing like plan 8's local-ahead machinery). Campaign streams are ALWAYS synced (no offline-first campaign editing in v1): pending events queue while disconnected but the UI shows the plan-8 sync badges.
4. **Join/leave ordering** (mirrors are two client appends, server-verified): JOIN = (a) char socket `character.campaign_joined {campaignId}` → ack, then (b) campaign socket `campaign.character_joined {characterId, ownerId: self, name}` (server mirror-verifies (a) committed). LEAVE = (a) char socket `character.campaign_left` FIRST, then (b) campaign `campaign.character_left` (server requires char-side current ≠ this campaign). Partial states are legal (doc-03 "no half-joins" is enforced by the mirror check, recovery = retry (b)); the UI surfaces "link incomplete — retry" on (b) rejects.
5. **Roll publishing**: `RollEntry` gains `formula: string`, `kind: RollLoggedV1['kind']`, `characterId?` — the play-tab roller composes them today already except formula/kind (derive from the existing dialog inputs). In campaign context the roll dialog gets a visibility picker (ruling: default `settings.visibility.rolls`, `private` shown only if `allowPrivateRolls`); publishing appends `roll.logged` to the campaign stream AND keeps the session-local RollLogService entry (solo behavior unchanged outside campaigns).
6. **Claim flow** (pregens, doc-02 L178-179, ADR-004): pregen = DM-created character (owner = DM) joined to the campaign. Claim by member M: (a) DM appends `character.owner_transferred {toUserId: M}` on `char:<id>` — EXECUTION-TIME VERIFY server-side that CharacterActor's meta hook updates `meta.ownerId` on `owner_transferred` (the plan-9 survey suggests only `character.created` sets it); if missing, Task 12 adds the hook + tests in `apps/api` (small, matrix-supported: doc-08 L61-62 grants DM `owner_transferred` for pregens); (b) roster re-point under first-writer-wins: DM appends `character.campaign_left` on char:<id> via gateway + `campaign.character_left` (the plan-9 final review verified the DM can complete both halves), then M performs the normal JOIN of ruling 4 with their now-owned character. The claim UI drives this sequence with per-step retry; every step is an ordinary already-shipped server rule — NO new server permission logic.
7. **Edit-outside-session**: `houseRules.editOutsideSession` enforcement is client UX (server stores the setting only — plan-9 ruling): `free` = no-op; `locked` = member (non-DM) mutating sheet actions disabled outside `session.active` with an explanatory banner; `dmApproval` = v1 renders as locked with a distinct notice key (`campaigns.edit.dmApprovalV1`) — no approval queue in v1, OWNER-FLAG in code + report. DM exempt; solo characters (no campaignId) exempt.
8. **Party overview publishing**: after each committed local append on a campaign-linked character, the owning device derives `PartyOverviewUpdatedV1['overview']` from the Sheet (hp/ac/level/classes/conditions/concentration/portraitThumb/passivePerception — exact schema fields) and appends `party.overview_updated` to the campaign stream, debounced ≥5 s and skipped when unchanged (deep-equal). Rendered in the party grid for everyone; `partySheets: 'full'` additionally enables DM (and only DM) sheet-subscribe drill-in.
9. **Campaign export** (DM): v1 exports the CAMPAIGN stream only — manifest + campaign events NDJSON via the fflate lazy-chunk `.hero`-bundle patterns (new format id `herokeep-campaign`, format:1). Member character events are NOT included (ownership/privacy) — OWNER-FLAG if party-inclusive export is wanted later. No import in v1 (server has no campaign-import route) — export is a backup artifact; document in the export dialog.
10. **QR**: the QR encodes `<origin>/join/<code>`; `/join/:code` (authGuard) pre-fills the join screen. Lib lazy-loaded in the lobby chunk; if execution-time verification finds no acceptable pinned lib, ship link-copy + grouped code display and OWNER-FLAG the QR (roadmap names it, so try hard first).
