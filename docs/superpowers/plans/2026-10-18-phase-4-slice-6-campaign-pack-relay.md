**Goal:** Close Phase 4: a DM enables installed content packs for a campaign, the server stores the pack JSON (ADR-008 :81-84) and serves it to members who auto-install and pin it, pack assets travel over the existing blob relay, the DM's party view derives each member against that member's own pinned packs, and the last engine carries (inventory item-id migration in rebase, the multiclass mastery combine rule as pack data, shared-cap-aware mastery offers) land so the roadmap's Phase 4 row can be marked complete.

**Architecture:** Pack bodies are too large for the 128 KB WebSocket frame, so they move over HTTP: a DM-only `PUT /campaigns/:id/packs/:packId/:version` stores the canonical JSON through the already-existing `StreamStore.putPack` (unused since plan 9), and `pack.enabled@1` is accepted by the campaign actor only when a stored body with the event's sha256 exists. Members learn the enabled set from `welcome.packs` and the folded `pack.enabled`/`pack.disabled` events, fetch the body over `GET`, validate it exactly like a `.hero` bundle pack (the shared validator extracted from the hero reader) and install it through `PackStore.installContent`; assets arrive through the blob relay as a new wanted tier. The engine carries are additive protocol fields (`ItemUpdatedV1.itemId?`, `SystemEntitySchema.multiclass.masteryCount?`) with their consumers in `planRebase` and `derive/attacks.ts`.

**Tech Stack:** Existing monorepo (TS 6, Vitest 4, Zod, Hono API with Cloudflare + Node adapters, Angular 22 zoneless, Playwright). No new dependencies.

## Design rulings (baked in — verify cited data, do not re-litigate)

1. **Pack bodies over HTTP, truth in events.** `PUT /campaigns/:campaignId/packs/:packId/:version` (DM only; body = canonical pack JSON ≤ 5 MiB; stores via `StreamStore.putPack(packId, version, json)` keyed by the campaign stream; responds `{sha256}` bare hex) must precede `pack.enabled@1 {packId, version, sha256}`; the actor's `append` verifies the stored body's sha256 equals the event's (else `packMissing`). `GET /campaigns/:campaignId/packs/:packId/:version` (any member; `ETag: "<sha256>"`, `If-None-Match` → 304) serves the body. `pack.disabled@1` deletes the stored body in `applyMetaHooks`. The settings document's `CampaignSettings.packs` field stays unused and is documented as superseded by the events (protocol immutable; no removal).
2. **One version per `packId` per campaign.** The DO store's `packs(id PRIMARY KEY)` already enforces it; the actor's quota counts DISTINCT `packId`s (today it counts `(packId, version)` pairs — align), and `pack.enabled` for an already-enabled `packId` with a new version is a VERSION CHANGE (counts once; the client projection's last-wins fold at `campaign-projection.ts:221-224` already matches). `pack.disabled` ignores the version (projection :226-229 already does; the server hook filters by `(packId, version)` — align to `packId`).
3. **Welcome carries the enabled set.** `stream-actor.hello` already sends `welcome {streams}`; the campaign actor adds `packs: meta.packs.map(({packId, version, sha256}) → {id: packId, version, sha256})` (additive `WelcomePackSchema.sha256?`). The client (`stream-sync-session.handleWelcome`) hands `welcome.packs` to the campaign projection as the initial enabled set; folded events keep it current. The existing `NoticeMsg` key `pack.updated` is NOT used (events suffice).
4. **Members install automatically, pin by choice.** When a campaign's enabled set contains a pack not installed on the device, `CampaignPacksService` fetches, validates and installs it (toast `campaigns.packs.installed`), then a sheet banner on every character LINKED to that campaign whose pins lack enabled packs offers "Pin campaign packs" (one click → the existing pin path with the rebase report when needed). Pinning is never forced (the DM party view derives members with their own pins — ruling 6). A pack the device cannot validate (conflict, invalid) shows the error in the campaign settings packs section and is never installed.
5. **Pack assets ride the blob relay.** `BlobTransferService.computeWantedForCampaign` adds a P3 tier: every `assets[].hash` of the campaign's enabled packs that the device has installed but whose blob is absent; holders (the DM at least) announce pack-asset hashes they hold in `blob.have` (cap 512 per connection — 6 packs × ~150 fits, `blob-relay.ts:65`). Received bytes are verified (`sha256Hex`) and stored `origin:'peer'`; plan 15 already protects pack-listed hashes from sweeps. No server storage of assets.
6. **DM party view uses the member's pins.** `ForeignCharacterSession.recompute` derives with `indexFor(facts.pins)` (new port method `ForeignCharacterEnginePort.indexFor(pins)`); non-core pins not installed on the DM's device → status `'warning'` with the missing list (the member-sheet dialog shows it; unresolved chips render as on the member's device); the core-version mismatch stays `'error'`. Name lookups in `member-sheet-dialog` and `dm-effects-panel` use the member's index.
7. **Inventory item-id migration** = additive `ItemUpdatedV1.itemId?` (reducer sets `entry.itemId`); `planRebase` emits `item.updated@1 {instanceId, itemId: <replacement>}` for every inventory entry whose `itemId` resolves in `next` to an entity with `deprecated.replacedBy` (chain-walked like decisions), after the decision events and before `decision.cleared`. Legacy logs without the event derive as before. The `pack-updated-v2` golden re-pins (sickle regains `nick`) with a note.
8. **`selection.count` shrink is reported**: a decision whose selection length exceeds the choice's count under `next` → `InvalidDecision {reason: 'count-reduced'}` with NO automatic clearing (the player trims it; the report label ×3). Engine-type-only union widening.
9. **Mastery combine rule becomes pack data**: `SystemEntitySchema.multiclass.masteryCount?: z.enum(['max','sum']).optional()` (default `'max'` when absent — matches today); `packages/content/src/static/system.ts` sets `'max'` with the OWNER-FLAG citation (PHB-sourced, SRD-silent); `derive/attacks.ts:222-227` reads it. Pack validation accepts both values; a golden pins each (synthetic fixture pack for `'sum'`).
10. **Shared-cap-aware mastery offers**: for a later class's `weapon-masteries` choice, the OFFERED count = `max(0, cap − masteries already granted by earlier classes' honoured picks)` (cap per ruling 9); count 0 → the choice is not offered (and not required for level-up); recorded decisions keep granting up to the cap exactly as today. Mechanism lives beside `masteryChoiceIds` in `derive/attacks.ts` and is consulted by `offeredRowChoices`/`validateSelection` through a small engine hook (`choiceCountOverride(choice, facts, comp, index)`) — no slug special-case outside the existing `MASTERY_SLUG` constant.
11. **Out of scope, owner-flagged for later plans:** authoring the synthetic `@1/skills` choices (needs a `Choice` on the class or a `skillChoice` schema field — plan 17 candidate); homebrew merge across devices; retaining old core versions on device; `.hkpack` export from a device; the DM pushing pack UPDATES to members' characters (members update through their own Build tab — the campaign only changes the enabled version); server-side pack asset storage (doc-07 stays "relay only").
12. **No speculative vocabulary.** Every mechanism ships with its consumer and a test in the same task.

## Review Focus

1. A member joining a campaign with two enabled packs installs both automatically with sha256 verified against the events; a server body that does not match the event's sha256 (tampered or stale) is refused and nothing is stored (Task 2).
2. `pack.enabled@1` without a stored body — or with a body whose sha256 differs — is rejected by the campaign actor on BOTH adapters (conformance scenario), and the 7th distinct pack is rejected while a version change of an enabled pack is accepted (Task 1).
3. The DM opens a member's sheet whose pins include a pack the DM's device lacks: the dialog renders with a warning listing the pack, unresolved references show as chips, no exception (Task 5).
4. Rebase v1→v2 now migrates the inventory item id so the sickle regains mastery; a legacy log that was rebased before this plan (decision migrated, item not) still derives identically with the same `issues` (Task 6).
5. A member receives a pack's icon through the relay from the DM holder within the connect sequence, the blob is stored `origin:'peer'`, and neither sweep ever evicts it (Task 4).
